# EMS campaign-status view (Week 6)

A read-only admin view for the EMS. Each email sequence (a row in `campaigns`) shows sent, opened, clicked and unsubscribed counts. The page reads in this order: totals, then one row per campaign, then a per-email breakdown, then data notes that say what the numbers can and cannot tell you.

  ```bash
  psql "$DATABASE_URL" -f sql/campaign_status.sql
  ```

  The file opens a `READ ONLY` transaction and returns five result sets:
  1. per campaign
  2. per email
  3. data quality
  4. `send_log.status` values in use
  5. `suppression_list.reason` values in use

## How each number is counted

| Number | Source | Rule |
|---|---|---|
| Sent | `send_log` | Rows whose `status` is `sent`, `delivered` or `success`. The full list is `SENT_STATUSES` in `src/queries.js`. Every other status counts as *failed / other*. Result set 4 shows the real status values, so the list can be corrected. |
| Opened | `analytics_events` | Distinct `user_id` with `opened_at` set. |
| Clicked | `analytics_events` | Distinct `user_id` with `clicked_at` set. |
| Unsubscribed | `users` | **Inferred.** No table links an unsubscribe to a campaign. Each unsubscribe is attributed to the last `send_log` row that user received at or before `unsubscribed_at`. Unsubscribes with no earlier send are counted in the totals as *unattributed*. |
| Rates | | Opened ÷ sent, and clicked ÷ sent. |

Breakdown: the per-email table groups by `campaign_id`, `email_type` and `variant`, so A/B variants appear as separate rows.

`send_log` and `analytics_events` are each aggregated on their own before the join. Joining the raw tables would multiply rows.

## Data issues the view surfaces instead of hiding

- **Stored totals are stale.** `campaigns.total_sent`, `total_opened` and `total_clicked` are 0 on all five live campaigns, even though every campaign has status `sent`.
  - The view never uses those columns as results.
  - It shows them next to the computed counts and marks every mismatch with ≠.
- **Open and click tracking looks broken.** Gongju's row counts: `send_log` 51 rows, `analytics_events` 1 row. The view warns whenever tracked rows are less than half of successful sends, because then low open and click numbers say more about tracking than about readers.
- **`suppression_list` is not counted as unsubscribes.** It has 42 live rows, and the `reason` values are unknown. The view reports how many suppressed addresses have no matching unsubscribed user.

## Layout

```
src/queries.js           SQL builders and loadCampaignStatus(query), all inside BEGIN READ ONLY
src/render.js            one-page HTML view
server.js                GET /admin/campaigns (HTML) and /admin/campaigns/status (JSON)
sql/campaign_status.sql  the same queries for psql, generated by `npm run preview`
sql/schema.sql           local mirror of the EMS tables, for tests only
sql/fixture.sql          synthetic rows; emails use the example.test domain
scripts/                 PGlite fixture loader and the preview renderer
test/                    node:test checks against the fixture; every expected value can be worked out by hand
preview/                 rendered fixture page and JSON
```

## Run

```bash
npm install
npm test                 # 8 checks against an in-process Postgres (PGlite)
npm run preview          # writes preview/index.html and sql/campaign_status.sql
DATABASE_URL=postgres://readonly@host/ems npm start   # http://127.0.0.1:4010/admin/campaigns
```

`server.js` forces `default_transaction_read_only=on` on every connection. It binds to 127.0.0.1 because it has no auth of its own. To ship it inside the EMS Node service, which runs on port 4000, mount `createHandler()` behind the existing admin auth guard.

## Prior art checked

I looked at open-source email tools with campaign analytics: listmonk, OpenMail, Notifuse, Sequence and Loopletter. All of them assume their own event schema, so none can sit on the EMS tables. This view stays a small set of queries against the existing tables.
